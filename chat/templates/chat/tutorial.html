Where the LLM code lives

The actual LLM request is made in chat/views.py, inside chat_api(). The Python package ollama sends the prompt to an Ollama server, which loads and runs the configured model. This repository does not contain model weights, implement a neural network, or train a model. The HTML and JavaScript provide the chat interface and pass messages to Django.

How the pieces connect

When Ollama is configured to run locally, prompts are processed by the local Ollama service. Ollama chooses CPU/GPU execution based on its setup and available hardware; this Django code does not directly select a GPU. If Ollama is configured to use a remote host, the prompt goes to that host.

2. Setup

Install the model

Choose a model that fits your available memory. Ollama manages the model files and decides whether to use CPU or GPU based on its configuration and available hardware. The choices below are examples, not requirements imposed by this application:

ModelSizeNote
llama3.2:3b~2.0 GBUsed here, good general chat
llama3.2:1b~1.3 GBFaster, weaker
qwen2.5:3b~1.9 GBGood multilingual
phi3:mini~2.2 GBStrong reasoning for size
ollama pull llama3.2:3b
ollama run llama3.2:3b "hello"     # quick test
ollama ps                           # PROCESSOR column should say "100% GPU"
nvidia-smi                          # shows ollama using VRAM

Run the Django app

python3 -m venv .venv

To change the model, edit OLLAMA_MODEL in config/settings.py.

3. How a question is served (code walkthrough)

Step 1 - The browser keeps the conversation

This endpoint does not store conversation state between requests. Each request must include the previous turns that should be available as context. The page keeps them in a JavaScript array and sends the array each time:

const history = [];
history.push({ role: 'user', content: question });

fetch('/api/chat/', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'X-CSRFToken': csrf },
  body: JSON.stringify({ messages: history }),
});

Each message has a role (user or assistant) and content.

Step 2 - URL routing

# chat/urls.py
path('api/chat/', views.chat_api, name='chat_api')

Django matches /api/chat/ and calls the chat_api view.

Step 3 - The view validates the input

@require_POST
def chat_api(request):
    try:
        messages = json.loads(request.body)["messages"]
    except (ValueError, KeyError, TypeError):
      return HttpResponseBadRequest('Expected JSON: {"messages": [...]}')
  • @require_POST rejects any non-POST request.
  • The body must be JSON with a top-level messages key. Invalid JSON, a missing key, or an incompatible top-level value returns HTTP 400.
  • The dashboard sends Django's CSRF token in the request header. The endpoint does not add a separate user-authentication or rate-limit check.

Step 4 - Build the prompt for the model

SYSTEM_PROMPT = {"role": "system", "content": "You are a helpful, concise assistant."}

history = [SYSTEM_PROMPT] + [
    {"role": m["role"], "content": str(m["content"])}
    for m in messages
    if isinstance(m, dict) and m.get("role") in ("user", "assistant") and "content" in m
]

The system prompt defines the bot's behaviour and is always first. It is added on the server, and the browser may only send user/assistant roles, so a user cannot override it.

    1. User types a question and presses Send.
    2. JS adds it to history and POSTs the whole history to /api/chat/.
    3. Django validates it, prepends the system prompt.
    4. ollama.chat(stream=True) runs the model on the GPU.
    5. Tokens are yielded and streamed to the browser, which displays them live.
    6. The finished answer is stored in history for the next turn.

    5. Tips and troubleshooting

  • If the Ollama call raises an exception, the generator yields an error message as text instead of a structured JSON error response.
    • Slow or on CPU? Run ollama ps. If it is not 100% GPU, use a smaller model.
    • Out of memory: long conversations use more VRAM. Use llama3.2:1b or trim old messages.
    • "Error talking to Ollama": make sure the service is running (ollama serve or systemctl status ollama).
    • Slow generation? Run ollama ps to see whether CPU, GPU, or both are being used; try a smaller model if memory is limited.
    • Out of memory: a smaller model or shorter conversation may reduce memory use.
